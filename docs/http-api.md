# HTTP API: интерфейс для интеграции p4

Блок 1 добавляет HTTP-адаптер поверх ядра p3. Доступны только создание Job и чтение сохранённого состояния. Машиночитаемый контракт — [api/openapi.yaml](api/openapi.yaml), фабрика приложения — [api/app.py](../api/app.py).

## Граница с сервисом заданий

Предлагаемый интерфейс для согласования с участником блока 3 находится в [application/contracts.py](../application/contracts.py). Он не зависит от FastAPI, HTTP и БД. Перед объединением PR участникам связанных блоков нужно подтвердить этот интерфейс.

```python
class JobService(Protocol):
    def create_job(
        self, *, repository_url: str, profile: str, idempotency_key: str
    ) -> CreationResult: ...

    def get_job(self, job_id: str) -> JobView: ...
```

Методы синхронные: FastAPI вызывает обработчики в пуле потоков. `create_job` сохраняет задание и организует фоновую обработку; ожидать завершения проверки внутри HTTP-запроса не нужно. Сервис отвечает за устойчивую идемпотентность и безопасную работу с хранилищем из разных потоков.

`CreationResult` содержит `job: JobView` и `created: bool`. Для нового задания `created=True` даёт HTTP 202; для прежнего задания с тем же ключом и параметрами `created=False` даёт HTTP 200. Адаптер не хранит ключи и не определяет равенство параметров. Конфликт другого тела с прежним ключом сервис сообщает через `IdempotencyConflictError`.

`get_job` только читает сохранённые данные и возвращает `JobView`; отсутствие задания обозначается `JobNotFoundError`. Чтение не запускает Dispatcher и не обращается к GitHub.

## Формат JobView

| Поле | Что передаёт сервис |
|---|---|
| `id` | Непустой идентификатор, пригодный для одного сегмента URL |
| `state` | `core.job.JobState` |
| `created_at`, `updated_at` | Сохранённые `datetime` с часовым поясом |
| `report` | Сохранённый отчёт Dispatcher p3 для `done`, иначе `None` |
| `error` | Сохранённая причина отказа с полем `code` для `failed`, иначе `None` |
| `recommendations` | `None` либо объект со статусом `pending`, `ready` или `failed` по OpenAPI |

Сервис возвращает копии сохранённых данных. Адаптер не изменяет Job и не вызывает его переходы. Отчёт из Dispatcher остаётся в прежнем формате: `repository_url`, `profile`, `commit_sha`, `compliant`, `results`. На HTTP-границе он превращается в `job_id`, `repository_url`, `profile`, `commit_sha`, `requirements_met`, `checks`. Пример настоящего отчёта получен через Registry, Dispatcher и оба Tool в фикстуре `done_report` HTTP-тестов.

В `created` и `running` нет отчёта и причины отказа. В `done` есть пять уникальных проверок профиля `basic` и отдельное состояние рекомендаций. Найденное нарушение требования остаётся результатом `done` с `requirements_met=false`. В `failed` есть причина технического отказа, отчёта нет. HTTP 200 при чтении `failed` означает успешное чтение состояния, как предусмотрено контрактом p2.

Коды сохранённых отказов: `repository_not_found`, `github_access_denied`, `github_rate_limited`, `github_unavailable`, `interrupted`, `invalid_tool_parameters`, `snapshot_incomplete`, `tool_execution_failed`. Последние четыре добавлены в OpenAPI для отказов ядра p3 и восстановления после перезапуска. Сообщение для клиента выбирает адаптер по коду; исходные тексты исключений, SQL и пути он не возвращает. Неизвестный код или повреждённый отчёт дают безопасный HTTP 500.

Если рекомендаций ещё нет, ответ содержит `{"status": "pending"}`. Их отказ не удаляет формальный отчёт: наружу выдаётся `recommendation_generation_failed` с безопасным сообщением.

## Валидация и ошибки

JSON-тело должно быть объектом только с полями `repository_url` и `profile`. URL — HTTPS-ссылка вида `https://github.com/owner/repository`, без query, фрагмента и учётных данных; допустим завершающий `/`. Существование и публичность проверяются адаптером GitHub, а не регулярным выражением. Поддерживается профиль `basic`. Заголовок `Idempotency-Key` обязателен и не может состоять только из пробелов.

Лимиты из OpenAPI: URL — 2048 символов, профиль — 64, ключ — 128, тело — 65536 байт. Размер тела проверяется по реально полученным байтам, включая потоковый запрос без `Content-Length`. Неизвестные поля, в том числе `status`, `id` и `report`, отклоняются до вызова сервиса. Некорректный JSON, включая `NaN` и `Infinity`, не принимается.

У ошибок одно тело:

```json
{"error": {"code": "validation_error", "message": "Request validation failed.", "details": [{"field": "profile", "issue": "Only the basic profile is supported."}]}}
```

| Причина | HTTP | `error.code` |
|---|---|---|
| Некорректный JSON | 400 | `invalid_json` |
| Прежний ключ с другими параметрами | 409 | `idempotency_key_conflict` |
| `InvalidStateTransition` при создании | 409 | `invalid_state_transition` |
| `OperationNotSupported` при создании | 409 | `operation_not_supported` |
| Слишком большое тело | 413 | `payload_too_large` |
| Content-Type отличается от application/json | 415 | `unsupported_media_type` |
| Неверные поля или отсутствующий ключ | 422 | `validation_error` |
| Превышен лимит поля | 422 | `field_too_long` |
| `UnknownOperationError` при создании | 422 | `unknown_operation` |
| `InvalidJobParametersError` при создании | 422 | `invalid_tool_parameters` |
| `JobNotFoundError` при чтении | 404 | `job_not_found` |
| Неизвестный маршрут / неподдерживаемый метод | 404 / 405 | `route_not_found` / `method_not_allowed` |
| Неожиданный отказ сервиса, БД или неверный сохранённый ответ | 500 | `internal_error` |

Ошибки `InvalidJobParametersError` и `IdempotencyConflictError` из [application/errors.py](../application/errors.py) принимают кортеж имён полей `fields`. HTTP-слой выдаёт только известные публичные имена полей. Сырые сообщения исключений не включаются в ответ. Ошибки выполнения Tool, сохранённые в `Job.failed`, читаются как состояние задания; таблица выше описывает ошибки обработки самого HTTP-запроса.

## Подключение и запуск

В точке сборки участника интеграции нужно создать настоящий сервис и передать его фабрике:

```python
from api.app import create_app

# service — реализация JobService с репозиторием, worker и адаптером GitHub.
app = create_app(service=service)
```

Затем этот модуль запускается Uvicorn по схеме `python -m uvicorn <модуль_сборки>:app`. Конкретная общая команда появится в README после интеграции остальных блоков. Сейчас `python -m uvicorn api.app:app --host 127.0.0.1 --port 8000` открывает Swagger `/docs` и схему `/openapi.json`, но не подключает хранилище: корректные операции с Job дают `500 internal_error`.

### Жизненный цикл worker и ресурсов

Фабрика также принимает `create_app(service=None, *, lifespan=None)`. `lifespan` — асинхронный контекстный менеджер FastAPI, принадлежащий точке сборки. Он может подключить сервис через `app.state.job_service` перед `yield`; HTTP-обработчики получают актуальный сервис при каждом запросе. Переданный заранее `service` по-прежнему поддерживается. Методы управления worker не добавляются в протокол `JobService`.

Пример структуры точки сборки (`open_runtime` реализуется при интеграции блоков 2–4, это не готовый импорт из этого PR):

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI

from api.app import create_app


@asynccontextmanager
async def lifespan(app: FastAPI):
    async with open_runtime() as runtime:
        app.state.job_service = runtime.service
        try:
            yield
        finally:
            app.state.job_service = None


app = create_app(lifespan=lifespan)
```

Контекст `open_runtime` в точке сборки отвечает за следующий порядок:

1. Открыть хранилище с уже применёнными миграциями и клиент GitHub, собрать сервис и worker. Миграции запускаются отдельной командой, а не созданием таблиц при старте HTTP.
2. Выполнить восстановление прерванных заданий по правилам ядра и запустить worker до передачи управления HTTP-серверу. Если запуск не удался, закрыть уже открытые ресурсы и передать ошибку старта серверу.
3. При штатном завершении после окончания обработки HTTP-запросов прекратить получение новых заданий worker и дождаться его остановки. После этого закрыть клиент GitHub и хранилище. Закрывать их, пока worker ещё работает, нельзя.

Worker, остановка с ожиданием, восстановление заданий и очистка ресурсов при частичном старте реализуются в точке сборки и сервисе заданий. HTTP-фабрика передаёт жизненный цикл FastAPI, но не запускает Dispatcher и не создаёт инфраструктуру сама. При аварийном завершении процесса выполнение shutdown не гарантируется; устойчивое восстановление обеспечивают сохранённое состояние и следующий запуск сервиса.

Сквозные тесты интеграции должны запускать то же приложение через контекст `with TestClient(app)`, чтобы выполнились startup и shutdown. [test_lifespan.py](../tests/api/test_lifespan.py) отдельно проверяет позднее подключение сервиса, ожидание фоновой задачи перед закрытием ресурсов при успешном и ошибочном HTTP-ответе, а также отказ старта с очисткой ресурсов. Это проверки интеграционного интерфейса фабрики; сохранение Job после перезапуска проверяется на настоящем хранилище в общих тестах.

В production-коде этого блока нет временного хранилища, заглушки успешной проверки или реализации идемпотентности в памяти. Подставной сервис используется только в HTTP-тестах. Проверка выживания Job после перезапуска, транзакций, миграций и настоящей идемпотентности требует следующих блоков p4.

## Проверки и доказательства для общего отчёта

Общая команда: `python -m pytest -q`. HTTP-тесты: `python -m pytest tests/api -q`.

- [test_http.py](../tests/api/test_http.py) проверяет создание, все состояния, преобразование реального отчёта Dispatcher, ошибки, отклонение недопустимых полей, ограничения размера и отсутствие внутренних сведений.
- [test_contract.py](../tests/api/test_contract.py) проверяет фактические ответы всех заявленных HTTP-статусов по OpenAPI, примеры в контракте, набор операций и ограничения входных полей.

Для раздела «Наш API против нарушений» сейчас есть доказательства по Н41 (поля состояния и результата отклоняются, маршрута смены состояния нет) и Н45 (нарушения ограничений входных данных отклоняются до сервиса). Проверки отсутствия внутренней трассы и SQL также находятся в HTTP-тестах. Итоговую таблицу Н40–Н49 нужно составлять по интегрированному сервису: HTTP-тест с подставным сервисом не доказывает устойчивую идемпотентность, права доступа или атомарность транзакций.
