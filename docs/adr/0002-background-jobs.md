# ADR-0002. Фоновое выполнение Job вместо ожидания в HTTP-запросе

- **Дата:** 2026-11-14
- **Статус:** предложено к принятию в практике 2 (на согласовании команды)

## Контекст и ограничения

Проверка публичного репозитория зависит от GitHub API и может занимать непредсказуемое время. Пользователю нужно создать Job, затем отдельно узнать статус и получить сохранённый отчёт (SC-01, SC-02). Запрос с тем же ключом идемпотентности не должен создавать второе задание (SC-04). Результат и commit SHA должны переживать повторное чтение и перезапуск приложения с сохранённой БД (AC-04, AC-06).

Архитектура уже выделяет HTTP-слой, сервис заданий, фоновый обработчик, Dispatcher и PostgreSQL. Состояния Job: `created`, `running`, `done`, `failed`; завершённые Job не перезапускаются (SC-03 и жизненный цикл). В первой версии нет аутентификации и владельцев заданий; идентификатор Job — UUID, а не последовательное число (SC-02).


В первой версии предусматривается один активный экземпляр приложения с одним фоновым обработчиком. Одновременная работа нескольких экземпляров не поддерживается. Поэтому при перезапуске оставшиеся в состоянии `running` задания считаются прерванными и переводятся в `failed` с причиной `interrupted`. Для горизонтального масштабирования потребуется отдельный механизм определения владельца и состояния выполняемых заданий.


## Решение

**HTTP-запрос принимает и сохраняет Job, а получение снимка и формальные проверки выполняет фоновый обработчик.** Клиент получает `job_id` и опрашивает статус/отчёт отдельными запросами.

1. Сервис заданий проверяет корректность входных данных и идемпотентность, сохраняет новый Job в PostgreSQL со статусом `created`, возвращает его UUID. Повтор тех же параметров с тем же ключом возвращает существующий id; другие параметры с тем же ключом дают конфликт, не изменяя прежний Job.
2. Фоновый обработчик атомарно захватывает сохранённый `created` Job, чтобы два исполнителя не начали его одновременно; Dispatcher через адаптер GitHub получает и сохраняет commit SHA. Пока SHA не получен, Job остаётся в `created`.
3. Механизм захвата должен обеспечивать освобождение задания `created` после аварийного завершения процесса, например за счёт транзакционной блокировки PostgreSQL. После перезапуска фоновый обработчик повторно выбирает такие задания из БД. Если commit SHA уже сохранён, используется именно он; иначе SHA получается и фиксируется перед переходом в `running`. Повторная обработка `created` не создаёт новый Job и не изменяет уже зафиксированный SHA.
4. После фиксации SHA выполняется переход `created → running`; оба формальных Tool получают данные **того же коммита**.
5. Dispatcher агрегирует результаты и сохраняет полный формальный отчёт **атомарно** с переходом `running → done`. Наличие нарушений требований означает `done`, а не `failed` (SC-06).
6. При обработанном техническом отказе до получения SHA выполняется `created → failed`, во время проверок — `running → failed`. При аварийном завершении процесса в состоянии `created` применяется восстановление, описанное в пункте 3. При перезапуске сервиса оставшиеся в БД задания со статусом `running` переводятся в `failed` с машиночитаемой причиной `interrupted`; выполнение таких заданий не возобновляется. Для каждого отказа сохраняется машиночитаемая причина, полного отчёта нет. Запрещённые переходы отклоняются правилами Job.
7. Чтение статуса или сохранённого отчёта идёт из БД и не запускает повторную проверку GitHub. В первой версии публичная отмена Job и автоматический перезапуск терминального `failed` **не поддерживаются**; новая попытка требует нового задания и нового ключа.

Компонент рекомендаций не является условием успешности формальных проверок: его технический отказ не должен уничтожать сохранённый формальный отчёт (граница из README). Конкретное хранение и выдача рекомендаций согласуются отдельно.

## Рассмотренные альтернативы

1. **Выполнять всё синхронно внутри `POST /jobs`.** Упрощает первый прототип, но клиент зависит от задержек GitHub API; при обрыве соединения сложнее понять, завершилась ли работа. Это противоречит выбранному сценарию с выдачей `job_id` и последующим чтением.
2. **Использовать внешний брокер задач/отдельный сервис очереди с первого дня.** Может дать более гибкое масштабирование и доставку заданий, но добавляет инфраструктуру, конфигурацию и отдельные правила согласованности с PostgreSQL. Для первой версии достаточно выделенного обработчика поверх сохраняемых Job; брокер пока не обязателен.

## Последствия и цена решения

**Плюсы:** быстрый ответ на создание Job без ожидания всех проверок, сохранённая история состояний, повторяемое чтение результатов, единая проверяемая версия репозитория и более ясная обработка идемпотентных повторов.

**Цена:** требуется координация HTTP-слоя и обработчика, безопасный захват Job, хранение промежуточных состояний и обнаружение прерванной работы. При старте сервиса необходимо обнаруживать сохранённые `running` и атомарно переводить их в `failed` с кодом `interrupted`, не перезапуская проверки. Пользователь теряет возможность автоматически продолжить прерванную проверку и должен создать новый Job с новым ключом. Конкретные таймауты и механика захвата согласуются при реализации. Сам по себе `async def` этих гарантий не обеспечивает.

Ограничение первой версии: нет публичной операции отмены и повторного запуска того же терминального Job. Это упрощает автомат состояний, но пользователю для новой попытки нужен новый Job.

## Условия пересмотра

Решение пересматривается при требованиях отмены, автоматического повторного выполнения заданий в состояниях `running` или `failed` после сбоя обработчика, значительного роста нагрузки, приоритетов очереди, горизонтального масштабирования исполнителей или необходимости гарантий доставки от отдельного брокера. Такие изменения потребуют пересмотра переходов Job, API и механизма захвата/восстановления работы.
