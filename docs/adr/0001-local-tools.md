# ADR-0001. Локальное выполнение формальных Tool

- **Дата:** 2026-11-14
- **Статус:** предложено к принятию в практике 2 (на согласовании команды)

## Контекст и ограничения

Сервис анализирует публичные учебные репозитории GitHub по заранее заданному профилю `basic`. Для первой версии предусмотрены два независимых вида формальных проверок: наличие обязательных файлов и разделов README. Они работают с одним снимком репозитория, полученным адаптером GitHub по зафиксированному commit SHA.

По [README](../../README.md) первая версия не выполняет код проверяемого репозитория, не требует пользовательских плагинов и не обращается к LLM для формальных проверок. В [архитектуре](../architecture.md) показаны Python/FastAPI, `Dispatcher`, `Registry`, два Tool и адаптер GitHub. Нужна возможность добавлять проверки, не переписывая Dispatcher.

## Решение

**В первой версии оба формальных Tool выполняются локально в том же процессе, что и `Dispatcher`, без выделения отдельных сервисов для инструментов.** При этом выполнение Job остаётся фоновым относительно HTTP-запроса, согласно [ADR-0002](0002-background-jobs.md). Взаимодействие с инструментами осуществляется через единый [контракт Tool](../tool-contract.md): `Registry` сопоставляет профиль с реализациями, а `Dispatcher` вызывает их без знания деталей алгоритмов.

- `required_files` проверяет обязательные пути по дереву файлов снимка;
- `readme_sections` проверяет заголовки в содержимом README того же снимка;
- инструменты не обращаются к GitHub API или БД напрямую, не запускают непроверенный код и не выполняют сетевые повторы;
- сетевой доступ и нормализация ошибок GitHub остаются в адаптере, сохранение отчёта — в Dispatcher/слое хранения;
- добавление новой формальной проверки требует реализации Tool и регистрации в профиле, но не ветвления по её типу внутри Dispatcher.

`ToolResult` содержит отдельные результаты требований; нарушение (`status: false`) — не техническая ошибка. Компонент рекомендаций остаётся отдельным от формальных Tool и не изменяет итог их проверки.

## Рассмотренные альтернативы

1. **Отдельный микросервис для каждого Tool.** Даёт независимое масштабирование и раздельную поставку, но добавляет сетевые вызовы, протоколы, эксплуатацию, межсервисные отказы и версионирование контракта. Для двух локальных проверок эта стоимость пока не оправдана.
2. **Встроить все проверки непосредственно в Dispatcher.** Проще на первом шаге, но Dispatcher начинает знать формат README и правила каждого профиля; добавление проверки требует менять общий сценарий и повышает риск регрессии.

## Последствия и цена решения

**Плюсы:** меньше инфраструктуры и сетевых отказов; все проверки работают над одним подготовленным снимком; проще тестировать Tool независимо и расширять набор проверок через Registry.

**Цена:** инструменты используют ресурсы и релиз приложения совместно; ресурсоёмкая реализация может повлиять на остальные проверки; ошибки в коде Tool могут повлиять на рабочий процесс. Для изоляции нужны ограничения исполнения и тесты, а для независимой поставки в будущем потребуется менять размещение и часть контрактов. Локальное выполнение само по себе не гарантирует отсутствия ошибок.

## Условия пересмотра

Решение пересматривается, если хотя бы один Tool потребует длительных задач, GPU/особых зависимостей, изоляции недоверенного кода, независимого масштабирования или выпуска отдельной командой. Тогда возможно вынести **только такой Tool** во внешний сервис через адаптер, сохранив общий интерфейс Dispatcher там, где это осуществимо.
