# Контракт Tool для проверки учебных репозиториев

**Статус:** проект контракта для практики 2; подлежит согласованию с контрактом API и реализацией Dispatcher.

Документ определяет единое внутреннее взаимодействие `Dispatcher` с инструментами проверки (`Tool`). Он конкретизирует компоненты из [архитектуры](architecture.md) и требования [SC-01, SC-03, SC-06](requirements.md). Формат внешних HTTP-ответов задаётся отдельно в `docs/api/openapi.yaml`.

## 1. Назначение и границы

- `Dispatcher` выбирает нужные реализации через `Registry` и вызывает их через **один контракт**.
- `Tool` выполняет одну разновидность формальной проверки над **снимком одного зафиксированного коммита**. Инструмент не выбирает актуальную ветку, не получает новый SHA и не обращается к GitHub API.
- Снимок готовит адаптер GitHub до запуска проверок. `Tool` не изменяет репозиторий, Job или БД; сохранение результатов и переходы Job находятся в ответственности `Dispatcher` и адаптера хранения.
- Компонент рекомендаций — отдельный компонент архитектуры, **не** один из двух формальных `Tool` этого контракта. Отказ рекомендаций не должен менять формальные результаты.

## 2. Общий интерфейс

Это **описание внутреннего контракта**, а не требование уже существующей реализации на Python. Эквивалентное представление в типах:

```python
class Tool(Protocol):
    name: str

    def execute(self, call: ToolCall) -> ToolResult | ToolError:
        ...
```

`ToolResult` означает, что инструмент **выполнил проверку** (включая обнаруженные нарушения). `ToolError` означает, что инструмент **не смог корректно выполнить** проверку по технической или контрактной причине. Эти два исхода нельзя смешивать.

**Способ передачи ошибки:** `execute` **возвращает** объект `ToolError` как один из двух вариантов результата; ожидаемые ошибки контракта не выбрасываются как исключения. `Dispatcher` проверяет тип возвращённого значения: при `ToolResult` собирает результаты проверок, при `ToolError` обрабатывает технический отказ. Непредвиденные исключения реализации не являются третьим предусмотренным исходом: их нужно перехватить на границе вызова и преобразовать в `tool_execution_failed`, не раскрывая внутренних деталей в сообщении об ошибке.

### Вход: `ToolCall`

| Поле | Тип | Значение |
|---|---|---|
| `snapshot` | `RepositorySnapshot` | Неизменяемый набор данных одного коммита, подготовленный адаптером GitHub. |
| `params` | object | Конфигурация конкретного Tool, полученная из выбранного профиля. |

`RepositorySnapshot` содержит:

| Поле | Тип | Значение |
|---|---|---|
| `repository_url` | string | Адрес публичного репозитория GitHub, для которого создан Job. |
| `commit_sha` | string | Уже зафиксированный commit SHA; **все** переданные данные относятся к нему. |
| `paths` | array[string] | Полный перечень путей файлов в репозитории на данном SHA, относительно корня. |
| `text_files` | map[string, string] | Содержимое нужных текстовых файлов на том же SHA; для `basic` — `README.md`, **если он существует**. |

Условия корректности снимка:

1. Пути относительные, в формате `/`, без `..`; имена сравниваются как указано в профиле. Нельзя использовать файлы из другого коммита.
2. Если `README.md` **отсутствует** в `paths`, его отсутствие в `text_files` — ожидаемая ситуация, а не ошибка загрузки.
3. Если `README.md` **есть** в `paths`, но его содержимое не было получено из-за отказа источника, нельзя выдавать это за нарушение разделов: снимок неполный, проверка завершается технической ошибкой.
4. Адаптер GitHub отвечает за получение и целостность снимка; `Tool` не повторяет сетевые запросы и не управляет сетевыми таймаутами.

### Выход при выполненной проверке: `ToolResult`

```json
{
  "tool": "required_files",
  "results": [
    {
      "check_name": "file:README.md",
      "status": true,
      "details": "Файл README.md присутствует в корне репозитория."
    },
    {
      "check_name": "file:CONTRIBUTING.md",
      "status": false,
      "details": "В корне репозитория отсутствует обязательный файл CONTRIBUTING.md."
    }
  ]
}
```

| Поле | Тип | Правило |
|---|---|---|
| `tool` | string | Зарегистрированное имя инструмента. |
| `results` | array[`CheckResult`] | По **одной записи на каждое** проверяемое требование, включая нарушенные. |
| `results[].check_name` | string | Уникальное в отчёте имя: `file:<путь>` или `section:<путь>:<заголовок>`. |
| `results[].status` | boolean | `true` — требование выполнено; `false` — проверка выполнена и выявлено нарушение. |
| `results[].details` | string | Непустое понятное пояснение об успехе или нарушении. |

`Dispatcher` объединяет `results` всех Tool в единый список отчёта и добавляет сведения о Job, репозитории, профиле, `commit_sha` и общем соответствии требованиям. `Tool` не присваивает состояние `done` или `failed`.

**Нарушение требований ≠ технический отказ.** Даже если один или все `CheckResult.status == false`, успешное выполнение всех проверок приводит к отчёту и состоянию Job `done` (SC-06, AC-14–AC-16).

### Технический или контрактный отказ: `ToolError`

```json
{
  "code": "invalid_tool_parameters",
  "message": "Список обязательных разделов должен быть непустым.",
  "details": {"field": "params.required_sections"}
}
```

| `code` | Когда применяется | Последствие |
|---|---|---|
| `invalid_tool_parameters` | Параметры вызова не соответствуют контракту конкретного Tool: отсутствует поле, неверный тип, пустой обязательный список. | Проверка не выполнена; ошибка передаётся `Dispatcher`. |
| `snapshot_incomplete` | Нарушен инвариант снимка: нет данных, которые должны быть получены для существующего файла, либо данные не соответствуют зафиксированному SHA. | Проверка не выполнена; отсутствие доступных данных не маскируется под `status: false`. |
| `tool_execution_failed` | Непредвиденный сбой реализации инструмента, который не является нарушением требований репозитория. | `Dispatcher` регистрирует техническую ошибку. |

Все ошибки содержат машиночитаемый `code`, понятный `message` и необязательный `details` с безопасными сведениями. Если проверка невозможна, не следует возвращать частичный успешный `ToolResult` как полный. Для ошибок выполнения формальных Tool `Dispatcher` инициирует технический переход Job `running → failed` согласно [архитектуре](architecture.md); преобразование в публичный формат определяется контрактом API.

**Не ответственность Tool:** неизвестный профиль или неизвестное имя инструмента обнаруживает `Registry` / вызывающий компонент; некорректные поля и превышение лимитов HTTP-запроса отсекает HTTP-слой (SC-05, AC-18: `413` для тела свыше 64 КБ и `422` для слишком длинного поля); ошибки GitHub API нормализует адаптер GitHub (SC-03). Прерывание фонового выполнения при перезапуске сервиса (`interrupted`) обрабатывает жизненный цикл Job, а не `Tool`: это не код `ToolError`.

## 3. Кто проверяет параметры

| Компонент | Проверяет |
|---|---|
| HTTP-слой | Формат публичного запроса: ссылка, обязательные поля, ключ идемпотентности. Ошибочный запрос не создаёт Job. |
| Сервис заданий / Registry | Допустимость профиля и выбор зарегистрированных инструментов. |
| Dispatcher / адаптер GitHub | Наличие и принадлежность данных одному зафиксированному SHA, подготовку снимка и передачу конфигурации Tool. |
| **Конкретный Tool** | **Авторитетную проверку своих параметров** (`required_paths`, `required_sections` и др.) и применение собственных правил проверки. |

Такая граница позволяет вызывать Tool из разных входных слоёв, а не полагаться только на валидацию HTTP.

## 4. Tool №1 — `required_files`

**Назначение:** проверить наличие каждого обязательного файла в полном перечне путей зафиксированного снимка; не читать содержимое файлов.

**Параметры:** `params.required_paths: array[string]` — непустой список уникальных относительных путей. Для профиля `basic`: `['README.md', 'CONTRIBUTING.md']`.

**Алгоритм и результат:** для каждого пути по порядку списка создаётся ровно один `CheckResult`:

- `check_name`: `file:<путь>`;
- `status: true`, если точный путь есть в `snapshot.paths`, иначе `false`;
- `details`: какой файл найден либо какой обязательный файл отсутствует.

Отсутствующий `CONTRIBUTING.md` или `README.md` — **нарушение**, а не `ToolError`. Нельзя сокращать список результатов из-за первого отсутствующего файла.

## 5. Tool №2 — `readme_sections`

**Назначение:** проверить обязательные заголовки в содержимом README того же коммита.

**Параметры:**

- `params.readme_path: string` — для `basic`: `README.md`;
- `params.required_sections: array[string]` — непустой список уникальных названий; для `basic`: `['Описание проекта', 'Запуск', 'Тестирование']`.

**Алгоритм и результат:** для каждого названия в исходном порядке создаётся один `CheckResult` с `check_name = section:README.md:<заголовок>`. Проверяется текст **заголовков Markdown**, а не произвольное вхождение слов в абзаце или блоке кода. Название сравнивается с элементом профиля после удаления внешних пробелов; требование к регистру букв сохраняется.

- Файл существует и заголовок найден → `status: true`, непустое пояснение.
- Файл существует, но заголовка нет → `status: false`, указать отсутствующий раздел.
- **Файл `README.md` отсутствует в `snapshot.paths`** → три `status: false` с пояснением, что разделы не найдены из-за отсутствия файла. Это позволяет показать **все пять** результатов профиля `basic` и сохранить Job в `done` при нарушениях (AC-16).
- Файл есть в дереве, но не удалось получить его текст → `snapshot_incomplete`, **не** ложный результат о нарушении.

Это правило для отсутствующего README уточняет поведение на границе между двумя Tool, не меняя требований SC-06.

## 6. Полный результат профиля `basic` и проверяемые случаи

`Registry` выбирает оба Tool; `Dispatcher` передаёт им **один и тот же** `RepositorySnapshot` и агрегирует пять записей, в согласованном порядке:

1. `file:README.md`
2. `file:CONTRIBUTING.md`
3. `section:README.md:Описание проекта`
4. `section:README.md:Запуск`
5. `section:README.md:Тестирование`

| Ситуация | Ожидаемое поведение |
|---|---|
| Все файлы и разделы есть | Пять результатов `status: true`; отчёт соответствует профилю; Job `done`. |
| Нет `CONTRIBUTING.md` | Для этого файла `status: false`, остальные проверки выполняются; Job `done`. |
| `README.md` есть, отсутствует раздел «Запуск» | Результат `section:README.md:Запуск` имеет `status: false`; Job `done`. |
| Нет самого `README.md` | `file:README.md` и все три проверки разделов — `false`; `CONTRIBUTING.md` проверяется отдельно; Job `done`. |
| GitHub вернул техническую ошибку при получении снимка | Адаптер сообщает причину по SC-03; не создаётся фиктивный список нарушений; Job `failed`. |
| Изменена основная ветка после фиксации SHA | Все Tool продолжают проверять данные **того же SHA**, результаты не смешиваются (AC-03). |

## 7. Версия и изменение контракта

**Редакция документа:** `1.0` (проект для практики 2). Это версия **внутреннего** соглашения между `Dispatcher` и `Tool`, а не номер публичного HTTP API. Изменения фиксируются в Git и проходят review.

- **Совместимые изменения** (например, добавление необязательного поля с безопасным значением по умолчанию) допускаются при условии, что существующие Tool и `Dispatcher` продолжают понимать старые вызовы и результаты.
- **Несовместимые изменения** (удаление или переименование поля, изменение его типа или смысла, изменение сигнатуры `execute` или модели возврата ошибок) нельзя вносить в один компонент изолированно: требуется согласованный PR с обновлением всех реализаций Tool, `Dispatcher`, документации и соответствующих проверок; редакция контракта повышается.
- Изменение внутреннего контракта не означает автоматического изменения HTTP API. Если меняется публичное поведение, соответствующие изменения отдельно согласуются с `docs/api/openapi.yaml`.
