# Требования к сервису проверки учебных репозиториев

## SC-01. Успешная проверка репозитория

**Цель:** получить воспроизводимый отчёт о соответствии публичного учебного репозитория выбранному профилю.

**Участник:** студент или преподаватель, обращающийся к API сервиса.

**Предусловия:** публичный репозиторий доступен через GitHub API, его основная ветка содержит коммит; встроенный профиль `basic` доступен; сервис и БД работают; ключ идемпотентности ранее не использовался. В репозитории присутствуют `README.md`, `CONTRIBUTING.md` и требуемые профилем разделы README.

### Основной поток

1. Пользователь отправляет ссылку на репозиторий, профиль `basic` и ключ идемпотентности.
2. Сервис проверяет параметры, сохраняет новое задание в состоянии `created` и возвращает его идентификатор.
3. Сервис начинает обработку задания и фиксирует commit SHA основной ветки репозитория — идентификатор проверяемой версии.
4. Сервис получает данные зафиксированной версии через GitHub API.
5. Сервис проверяет наличие обязательных файлов и разделов README по профилю `basic`.
6. Сервис сохраняет отчёт и отмечает задание как завершённое.
7. Пользователь получает отчёт по идентификатору задания.

### Критерии приёмки

**AC-01. Создание задания**

- **Дано:** выполнены предусловия сценария.
- **Когда:** пользователь отправляет корректный запрос проверки с новым ключом идемпотентности.
- **Тогда:** сервис возвращает идентификатор сохранённого задания; для получения отчёта не требуется повторно создавать задание.

**AC-02. Полнота успешного отчёта**

- **Дано:** GitHub API доступен и репозиторий соответствует профилю `basic`.
- **Когда:** обработка задания завершена.
- **Тогда:** состояние задания равно `done`; отчёт содержит идентификатор задания, репозиторий, профиль, commit SHA и список результатов всех проверок профиля `basic` в формате ниже. В данном успешном сценарии у каждого результата `status: true`; итог отчёта — требования выполнены.

Каждый элемент списка результатов содержит три обязательных поля:

| Поле | Тип | Смысл |
|---|---|---|
| `check_name` | string | Уникальное в пределах отчёта имя проверки: `file:<путь>` для файла или `section:<путь>:<заголовок>` для раздела |
| `status` | boolean | `true` — требование выполнено; `false` — проверка выполнена и обнаружено нарушение требования |
| `details` | string | Непустое пояснение: что найдено при успехе или какое требование нарушено |

В профиле `basic` возвращаются пять результатов: `file:README.md`, `file:CONTRIBUTING.md`, `section:README.md:Описание проекта`, `section:README.md:Запуск`, `section:README.md:Тестирование`.

Пример одного элемента списка в успешном отчёте:

```json
{
  "check_name": "file:README.md",
  "status": true,
  "details": "Файл README.md присутствует в корне репозитория."
}
```

`status` относится к результату отдельной проверки, а не к состоянию задания. Нарушение требования (`status: false`) не является техническим сбоем и само по себе не переводит задание в `failed`. Технические сбои, например недоступность GitHub API, обрабатываются как ошибки выполнения задания, а не как результат проверки со `status: false`.

**AC-03. Единая версия репозитория**

- **Дано:** сервис зафиксировал commit SHA для задания.
- **Когда:** сервис выполняет проверки обязательных файлов и разделов README.
- **Тогда:** все проверки используют один зафиксированный коммит, а его SHA указан в отчёте.

**AC-04. Сохранение результата**

- **Дано:** задание завершено и отчёт сохранён.
- **Когда:** пользователь повторно запрашивает отчёт, в том числе после перезапуска приложения с сохранённой БД.
- **Тогда:** сервис возвращает ранее сохранённые результаты и commit SHA без нового обращения к GitHub для повторного анализа.

## SC-02. Получение статуса и отчёта по заданию

**Цель:** узнать текущее состояние задания и получить сохранённый отчёт после завершения проверки, не создавая задание повторно.

**Участник:** студент или преподаватель, ранее создавший задание через API сервиса.

**Предусловия:**
- окружение: сервис и БД работают;
- состояние запроса: задание с указанным идентификатором существует в БД (для AC-07 — заведомо не существует).

### Основной поток

1. Пользователь отправляет идентификатор задания в запрос статуса.
2. Сервис находит задание в БД и возвращает текущее состояние: `created`, `running`, `done` или `failed`.
3. Если состояние не `done` и не `failed`, сервис возвращает только служебные поля (id, состояние, время создания/обновления); отчёт недоступен.
4. Если состояние `done`, сервис возвращает сохранённый отчёт: id задания, репозиторий, профиль, commit SHA, итог, результаты отдельных проверок.
5. Если состояние `failed`, сервис возвращает состояние и машиночитаемую причину отказа (см. SC-03); отчёт не возвращается.
6. Пользователь повторяет запрос статуса, пока задание не перейдёт в терминальное состояние.

### Критерии приёмки

**AC-05. Статус до завершения**
- **Дано:** задание в состоянии `created` или `running`.
- **Когда:** пользователь запрашивает статус по id.
- **Тогда:** сервис возвращает актуальное состояние; отчёт отсутствует или пуст; запрос не запускает обработку и не создаёт новое задание.

**AC-06. Статус завершённого задания**
- **Дано:** задание в состоянии `done`, отчёт сохранён в БД.
- **Когда:** пользователь запрашивает статус или отчёт по id.
- **Тогда:** сервис возвращает `done` и полный сохранённый отчёт (репозиторий, профиль, commit SHA, итог, результаты проверок); повторные запросы возвращают те же данные без обращения к GitHub для повторного анализа.

**AC-07. Неизвестный идентификатор**
- **Дано:** задания с указанным id в БД нет.
- **Когда:** пользователь запрашивает статус или отчёт.
- **Тогда:** сервис возвращает ошибку «задание не найдено» с понятным кодом ответа; новое задание не создаётся.

## SC-03. Ошибочный сценарий: репозиторий не существует или недоступен

**Цель:** получить воспроизводимую ошибку вместо «зависшего» задания, если проверяемый репозиторий нельзя прочитать через GitHub API.

**Участник:** студент или преподаватель, отправивший ссылку на репозиторий.

**Предусловия:**
- окружение: сервис и БД работают, GitHub API доступен как сервис (но отвечает ошибкой на конкретный репозиторий или не отвечает вовремя);
- состояние запроса: корректный по формату запрос проверки, новый ключ идемпотентности.

### Основной поток

1. Пользователь отправляет ссылку на несуществующий, удалённый, приватный или недоступный репозиторий, профиль `basic` и ключ идемпотентности.
2. Сервис проверяет параметры, сохраняет задание в `created` и возвращает id.
3. Сервис начинает обработку, обращается к GitHub API за commit SHA основной ветки.
4. GitHub API отвечает ошибкой:
 - 404 — репозиторий не найден или приватный;
 - 403 — либо превышение лимита (признаки: X-RateLimit-Remaining: 0, Retry-After, тело «rate limit exceeded»), либо запрет доступа;
 - 429 — превышение лимита;
 - 5xx — сбой на стороне GitHub;
 - таймаут или сетевой отказ — GitHub/сеть недоступны.
5. Сервис сохраняет машиночитаемую причину — repository_not_found, github_access_denied, github_rate_limited, github_unavailable — и переводит задание из created в failed (commit SHA не зафиксирован, проверки не начинались).
6. Пользователь запрашивает статус и получает `failed` с причиной; отчёт о соответствии требованиям не формируется.

**Различение 403.** 429 и 403 с признаками лимита (X-RateLimit-Remaining: 0, Retry-After, тело «rate limit exceeded») → github_rate_limited. Остальные 403 → github_access_denied. Если заголовки и тело не позволяют отличить запрет от лимита, адаптер возвращает github_access_denied — консервативно, чтобы не выдавать постоянную ошибку за «повторите позже».

### Критерии приёмки

**AC-08. Отказ GitHub API не ломает задание**
- **Дано:** GitHub API возвращает ошибку или не отвечает в отведённое время при получении commit SHA.
- **Когда:** обработка завершилась отказом.
- **Тогда:** состояние failed; задание сохранено в БД; в ответе есть машиночитаемая причина из набора repository_not_found / github_access_denied / github_rate_limited / github_unavailable; успешный отчёт не возвращается.

**AC-09. Воспроизводимость ошибки**
- **Дано:** задание в состоянии `failed`.
- **Когда:** пользователь повторно запрашивает статус, в том числе после перезапуска приложения с сохранённой БД.
- **Тогда:** возвращаются то же состояние и та же причина без повторного обращения к GitHub для повторного анализа.

> **Граница:** нарушение требований (задание `done`, итог «требования не выполнены») — не техническая ошибка; технический отказ — только `failed`.

## Жизненный цикл задания (Job)

**Состояния:**
- `created` — задание сохранено, обработка не начата;
- `running` — commit SHA зафиксирован, выполняются проверки этой версии;
- `done` — проверки завершены, отчёт сохранён (итог: выполнено / есть нарушения);
- `failed` — технический отказ (GitHub API, сеть, внутренняя ошибка), отчёт не формируется.

**Разрешённые переходы:**
- `created → running` — начата обработка, зафиксирован commit SHA;
- `running → done` — все проверки выполнены, отчёт сохранён;
- `running → failed` — отказ GitHub API/таймаут/внутренняя ошибка во время проверок;
- `created → failed` — отказ при получении commit SHA основной ветки (репозиторий не найден/приватный, запрет доступа, лимит, сбой или таймаут GitHub API).

**Запрещённые переходы:**
- `done → *` — завершённое задание неизменно;
- `failed → *` — не перезапускается в первой версии; новая попытка = новое задание с новым ключом идемпотентности;
- `* → created` — возврат в начальное состояние запрещён.

**Терминальные состояния:** `done`, `failed`.
