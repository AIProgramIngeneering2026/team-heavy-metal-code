# Правила совместной разработки

Документ описывает порядок работы команды над проектом «Проверка учебных репозиториев». Правила обсуждаются участниками команды в Pull Request. Предложения и замечания фиксируются в комментариях. Для утверждения правил требуется одобрение (Approve) как минимум одного другого участника с правами записи в репозиторий. После одобрения и объединения Pull Request с веткой `main` правила считаются принятыми.

## 1. Задачи (GitHub Issues)

- Перед началом работы создаём GitHub Issue с названием, описанием задачи, ожидаемым результатом и исполнителем.

- Если задача связана с пользовательским сценарием, указываем соответствующий сценарий и критерии приёмки из `docs/requirements.md`.

- В Pull Request (PR) добавляем ссылку на Issue, например `#12`.

- Если задача затрагивает общие форматы или состояния Job, заранее согласуем изменение с участниками, отвечающими за связанные части системы.

## 2. Ветки

- `main` — основная ветка с согласованными изменениями. Прямые push и force push в `main` запрещены.

- Для каждой задачи создаём отдельную ветку от актуальной `main`.

- Используем имена `<тип>/<номер-issue>-<краткое-описание>`:

    - `docs/12-contributing` — документация;

    - `docs/13-report-scenario` — сценарий получения отчёта;

    - `feat/14-repository-check` — новая функциональность;

    - `fix/15-invalid-url` — исправление ошибки;

    - `test/16-job-states` — тесты.

- Несвязанные изменения выполняем в разных ветках и PR. При совместном редактировании `docs/requirements.md` согласуем разделы и поочерёдно объединяем изменения, обновляя ветки от актуальной `main`.

## 3. Коммиты

- Один коммит отражает одно законченное, логически связанное изменение.

- Сообщение должно объяснять, что сделано; избегаем названий вроде `fix`, `changes` и `доработки`.

- Используем формат `<тип>: <краткое действие>`; например:

    - `docs: описать правила командной разработки`;

    - `docs: добавить сценарий получения отчёта`;

    - `fix: обработать некорректную ссылку на репозиторий`.

- Не смешиваем в одном коммите новую функцию, постороннее форматирование и исправление другой ошибки.

## 4. Pull Request

1. Автор завершает согласованную часть задачи в собственной ветке.

2. Создаёт PR в `main` командного репозитория и указывает:

    - связанную Issue;

    - что изменено и зачем;

    - как проверено изменение и какие ограничения остались.

3. Организует проверку PR другим участником команды: назначает проверяющего через Reviewers или договаривается о проверке в командном чате. Автор не одобряет собственный PR.

4. Исправляет существенные замечания; после значимых изменений повторно запрашивает проверку.

5. Перед объединением PR проверяет итоговый набор изменений и убеждается, что необходимые автоматические проверки пройдены для актуальной версии кода (если проверки настроены).

6. Объединяет PR с `main` только после одобрения другого участника и успешных обязательных автоматических проверок, если они настроены.

## 5. Code Review

- Проверяющий сначала читает Issue и описание PR, затем изучает изменённые файлы (`Files changed`).

- Для распределения review используем круговую схему: каждый участник проверяет PR следующего участника по согласованному командой списку. Если назначенный проверяющий недоступен или не знаком с затронутой областью, команда согласует замену.

- Проверяем соответствие задаче и критериям приёмки, понятность изменений, обработку ошибок, согласованность терминов и контрактов, обновление документации и тестов при необходимости.

- При проверке документации убеждаемся, что все обязательные разделы присутствуют, требования сформулированы однозначно, критерии приёмки проверяемы, а `README.md`, сценарии и состояния Job не противоречат друг другу.

- Review должно содержать содержательное замечание, предложение или вопрос по существу изменения. Формального `LGTM` недостаточно для учебной практики.

- Автор отвечает на замечания и вносит согласованные исправления. Нерешённые существенные вопросы блокируют объединение PR.

- В рамках первой практики каждый участник подтверждает личный вклад собственным влитым PR или содержательным review чужого PR. По возможности каждый участник выполняет оба действия.

## 6. Definition of Done (критерии готовности)

Задача считается завершённой, если:

- Выполнена цель Issue и проверены соответствующие критерии приёмки.

- Изменения согласованы с требованиями проекта, а при необходимости — с состояниями Job и контрактами компонентов.

- Добавлены или обновлены необходимые тесты (для задач с кодом); для документации проверены структура, читаемость, ссылки и согласованность формулировок.

- Обязательные автоматические проверки пройдены (если настроены).

- Создан PR со ссылкой на Issue и объяснением способа проверки.

- Получено одобрение другого участника; существенные замечания устранены.

- PR объединён с `main`, Issue закрыта или отмечена выполненной.

## 7. Учёт личного вклада

- Каждый участник сохраняет полные ссылки на свои влитые PR и/или PR, в которых выполнил содержательное review. Ссылки подтверждают личное участие в соответствующей практике.
- При подготовке отчёта `pN.md` команда указывает эти полные ссылки в разделе «Вклад участников» для соответствующей практики.
- В первой практике личное участие подтверждается ссылкой на собственный влитый PR или PR, в котором участник выполнил содержательное review. Рекомендуется представить оба вида участия.
- Один и тот же Pull Request может быть засчитан участнику в качестве подтверждения личного вклада только в одной практической работе.

## 8. Использование ИИ

Использовать ИИ как вспомогательный инструмент можно, но автор обязан проверить предложенные решения, исправить ошибки и уметь объяснить результат. Секреты, токены доступа и пароли не добавляем в репозиторий или промпты.
